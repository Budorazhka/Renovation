# Реферальная сеть BAZA: кураторы, команды, 7%

Модуль `referral-network`, очередь N-26, сделано 16.09.2026 по плану
[2026-09-16-mlm-curator-network](../plans/2026-09-16-mlm-curator-network.md).

## Решения владельца 16.09.2026

| Правило | Решение |
| --- | --- |
| Глубина сети | Один уровень: куратор и его команда |
| Сколько получает куратор | 7% от фактической комиссии агента из своей команды |
| С каких сделок | Только первичка |
| Размер команды | На старте 5–10, в идеале до 20, дальше собирать новую. Система подсказывает, не запрещает |
| Когда начисляется | Когда деньги пришли |
| Кто платит | BAZA |
| Кто отмечает деньги | Менеджер BAZA |
| Как попадают в команду | По ссылке куратора; суперадмин видит и правит всю сеть |
| Уход и смена куратора | Можно, в индивидуальном порядке — заявкой, решает BAZA |
| Кто становится куратором | Только проверенный BAZA — назначение суперадмином и есть проверка |
| Сотрудник агентства у куратора из другой компании | Нельзя, и для суперадмина тоже |
| Раздел «Партнёры» ERP | Отдельная программа, в эту сеть не входит |

## Модель

Сеть принадлежит платформе и привязана к человеку (Identity), а не к
должности: из агентства можно уйти, место в команде и история начислений
остаются.

| Коллекция | Что хранит |
| --- | --- |
| `referral_curators` | Кураторы: код приглашения, кто и когда назначил, снятие. Один действующий на человека |
| `referral_memberships` | Членство в командах: `active`, `on_review`, `ended`. Закрытое не перезаписывается — смена куратора видна историей |
| `referral_requests` | Заявки: стать куратором, уйти, сменить куратора. Одна нерешённая каждого типа на человека |
| `curator_accruals` | Начисления: куратор и агент на момент денег, сделка, фактическая комиссия, процент-снимок, сумма, `accrued` / `paid` / `reversed`. Одно живое на сделку |

В сделке CRM появились `commissionReceived`, `commissionReceivedAt`,
`commissionReceivedByAdminId` — фактические деньги, которые отметил менеджер
BAZA. Ожидаемая комиссия осталась планом.

## Как сделка становится первичкой

Тип хранится на сделке CRM (`dealType`: `primary`, `secondary`, `rental`,
`assignment`). Сделку из брони застройщика сервер сразу создаёт первичкой.
Сделку, которую агент завёл сам, по умолчанию считает вторичкой: агент
выбирает тип в карточке сделки ERP, вкладка «Финансы» (`POST /deals` и
`PATCH /deals/:dealId` принимают `dealType`).

До правки 16.09.2026 тип нельзя было передать ни при создании, ни при правке: в
живом продукте сделка агента всегда была вторичкой, и 7% куратору не
начислились бы ни разу. Интеграционный сценарий вставлял первичку прямо в
базу и этого не видел; теперь он идёт через `POST /deals` и `PATCH`.

Ошибиться типом безопасно: в «Комиссии» BAZA первичка только попадает, а
деньги отмечает менеджер BAZA. После его отметки тип зафиксирован — `PATCH`
со сменой типа отвечает 409 `DEAL_TYPE_LOCKED` (условие стоит и в фильтре
записи, так что гонка с отметкой его не обходит). Остальные поля сделки
правятся как раньше.

## Как считаются деньги

1. Менеджер BAZA отмечает в админке («Комиссии»), что по сделке первички
   пришла комиссия, — фактическую сумму, валюту и дату.
2. В той же транзакции: агент — тот, кто сейчас занимает должность владельца
   сделки; его открытое членство даёт куратора.
3. Если агент в агентстве другой компании, чем куратор, связь уходит
   `on_review`, начисления нет, пишется аудит. Снимает вопрос суперадмин —
   переводом или удалением.
4. Иначе пишется начисление: 7% от фактической комиссии, округление до
   минорной единицы, процент копируется в запись.
5. Менеджер BAZA отмечает выплату («Выплаты»): `accrued` → `paid`.
6. Снятие отметки о деньгах сторнирует начисление (`reversed`). Уже
   выплаченное сторнирует только суперадмин — иначе 409
   `CURATOR_ACCRUAL_ALREADY_PAID`.

Если начисления нет, ответ говорит почему: `not_primary`, `no_occupant`,
`not_in_team`, `membership_on_review`, `company_mismatch`, `curator_retired`.

## Маршруты

| Маршрут | Кто | Что |
| --- | --- | --- |
| `GET /marketplace/referral/me` | человек, кабинет | своя роль: куратор (код, команда, деньги), участник (куратор, начисления с его сделок), никто |
| `POST /marketplace/referral/join` | человек | вступить по коду ссылки |
| `POST /marketplace/referral/requests` | человек | заявка: стать куратором, уйти, сменить куратора |
| `GET /public/referral-invites/:code` | кто угодно, лимит по IP | имя куратора по ссылке — до регистрации |
| `GET /referral-network/me` | сотрудник ERP | то же, что кабинет |
| `GET /referral-network/organization` | руководитель, `referral_network.read` | кураторы компании и их команды, без денег |
| `GET /admin/referral-network` | `referral_network.read` | вся сеть: дерево, коды, деньги, сводка |
| `GET /admin/referral-network/people?login=` | `referral_network.read` | найти человека по почте |
| `GET /admin/referral-network/people/:id/history` | `referral_network.read` | история членства |
| `POST /admin/referral-network/curators` | `referral_network.manage` | назначить куратора |
| `POST /admin/referral-network/curators/:id/retire` | `referral_network.manage` | снять; команда закрывается |
| `POST /admin/referral-network/members` | `referral_network.manage` | добавить или перевести в команду |
| `POST /admin/referral-network/members/:id/remove` | `referral_network.manage` | убрать из команды |
| `GET /admin/referral-network/requests` | `referral_network.read` | очередь заявок |
| `POST /admin/referral-network/requests/:id/decide` | `referral_network.manage` | решить; одобрение применяет в той же транзакции |
| `GET /admin/commissions?received=` | `commission.confirm` | сделки первички всех организаций |
| `POST /admin/commissions/:dealId/received` | `commission.confirm` | деньги пришли + начисление |
| `POST /admin/commissions/:dealId/cancel` | `commission.confirm` | снять отметку + сторно |
| `GET /admin/curator-payouts` | `curator_payout.mark` | итоги по кураторам |
| `GET /admin/curator-payouts/:id/accruals` | `curator_payout.mark` | журнал начислений |
| `POST /admin/curator-payouts/:id/pay` | `curator_payout.mark` | отметить выплату |
| `PATCH /admin/people/:identityId` | `person.rename` | сменить имя человека с причиной; без должности — 409 `PERSON_WITHOUT_POSITION` |

Суперадмин проходит все админские права. Обычному администратору права
выдаются индивидуально (раздел «Аккаунты» в админке).

## Экраны

| Где | Что |
| --- | --- |
| Админка → «Сеть» | Дерево сверху вниз ([исследование](../research/2026-09-16-referral-tree-ux.md)): BAZA → ряд кураторов → команда «вешалкой» под раскрытым куратором (рядами по четыре, по двое с каждой стороны стержня). Команды свёрнуты, на карточке куратора — статус точкой и словом, размер команды и «+N» под вопросом. Сдвиг перетаскиванием и колесом, масштаб Ctrl+колесо и кнопками, «Уместить». Второй вид — списком с отступами. Поиск раскрывает ветку и подводит к человеку. Карточка выбранного: код, размер команды со шкалой 5–20, начислено/выплачено/к выплате, история. Поиск по почте, назначение, снятие, перевод, удаление — с обязательной причиной. Вкладка «Заявки» |

| Админка → «Выплаты» | Итоги по кураторам, журнал начислений с выбором к выплате |
| Маркетплейс → «Моя команда» (`/account/team`) | Куратор: ссылка, статус команды, деньги, дерево команды (куратор сверху, команда «вешалкой», на телефоне по одному с каждой стороны), журнал. Участник: куратор, начисления, заявки уйти или сменить куратора. Остальные: вступить по коду, заявка стать куратором |

| ERP → «Партнёры → MLM» | Своя команда деревом с деньгами или свой куратор; руководителю — кураторы компании карточками, команда раскрывается «вешалкой». Раньше пункт перекидывал на нарисованную аналитику города |
| ERP → карточка сделки → «Финансы» | Тип сделки (первичка, вторичка, аренда, переуступка), после отметки BAZA — только чтение; «Комиссия получена BAZA» только для чтения; агенту из команды — «Куратору начислено 7%» |

## Проверки

- `referral-rules.spec.ts` — 5: размер команды, 7% с округлением, процент-снимок, код приглашения, правило компании.
- `curator-accruals.service.spec.ts` — 6: вторичка, связь под вопросом, смена компании уводит под вопрос, снятый куратор, начисление, итоги.
- `referral-network.integration-spec.ts` — 5 сквозных на живой базе: ссылка → вступление → сделка агента через `POST /deals` (вторичка) → агент ставит первичку → деньги → 7% → смена типа запрещена (`DEAL_TYPE_LOCKED`) → выплата → сторно только суперадмином; правило компании для ссылки и для суперадмина, сеть компании в ERP без денег; смена куратора только заявкой; права админки; сделка без куратора и вторичка.
- Админка: раскладка дерева (7), страница сети (5, включая вид списком), комиссии (3).
- Маркетплейс: раскладка «вешалки» и страницы кабинета (6).
- ERP: раскладка «вешалки» и раздел MLM с раскрытием команды (3); тип сделки в адаптере и `DealsContext.changeType`, включая `DEAL_TYPE_LOCKED` (3).

## Демо-сеть и тестовые кабинеты

`scripts/demo/seed-referral-network.mjs` засевает стенд только через HTTP API,
как это сделали бы люди, — прямых записей в базу нет. Повторный запуск не
плодит дублей.

```
DEMO_ADMIN_LOGIN=<действующий суперадмин> DEMO_ADMIN_PASSWORD=<его пароль> \
  node scripts/demo/seed-referral-network.mjs
```

Что появляется:

| Кабинет | Логин | Где смотреть |
| --- | --- | --- |
| Суперадмин BAZA | `demo-superadmin@baza.demo` | админка: «Сеть», «Комиссии», «Выплаты» |
| Куратор Нино Беридзе, команда из 6 | `demo-mlm-nino@baza.demo` | маркетплейс «Моя команда», ERP «Партнёры → MLM» |
| Агент Георгий Абашидзе | `demo-mlm-giorgi@baza.demo` | ERP: сделка → «Финансы»; маркетплейс «Моя команда» |
| Куратор Ираклий Табидзе, команда из 3 | `demo-mlm-irakli@baza.demo` | статус «Идёт набор» |
| Руководитель «Агентство Batumi Home» | `demo-mlm-agency-owner@baza.demo` | ERP «Партнёры → MLM»: кураторы компании |
| Куратор-сотрудник Давид Церетели | `demo-mlm-david@baza.demo` | команда из двух коллег по агентству |

Пароль всех — `DEMO_PASSWORD`, на localhost по умолчанию `demoPass123`.
Сделки: четыре первички и одна вторичка; по трём первичкам BAZA отметила
деньги (7% куратору: 210, 294, 252 USD), одно начисление выплачено.

Первый прогон на стенде 16.09.2026 нашёл то, чего не показали превью: все
риэлторы назывались «Owner». Регистрация писала владельцу заглушку, имени не
спрашивала. Теперь ERP спрашивает «Ваше имя» (`ownerName` в
`POST /organizations/register`), а у зарегистрированных раньше независимых
риэлторов вместо заглушки показывается название организации — в сети,
«Комиссиях», команде ERP и рейтинге риэлторов.

## Что осталось

- Сверка экранов кабинета с макетом раздела MLM из Figma (секция CRM `2834:63037`).
- Виджет «Моя команда» на втором экране рабочего стола ERP.
- У владельцев агентств, зарегистрированных до поля «Ваше имя», осталась заглушка «Owner». Имя после регистрации меняет BAZA, не сам человек (решение владельца 16.09.2026): админка → «Сеть» → найти человека по почте → «Изменить имя», с причиной; старое имя остаётся в аудите.
- Экран «Расклад рефералов MLM» в аналитике владельца — не MLM, а программа партнёров городов (франчайзи); её правила ещё не обсуждались (владелец, 16.09.2026).
- Порога и графика выплат нет: информации нет (владелец, 16.09.2026). Менеджер BAZA отмечает выплату, когда решит; порог можно добавить позже, не трогая начисления.
