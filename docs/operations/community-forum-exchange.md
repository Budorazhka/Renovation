# Community: форум, биржа MLS, мероприятия (этап 11, частично)

Дата: 11.09.2026. Код — `f91f3d6` (10.09), исправления — `c01688e`, `735bc4d` (10.09),
N-02 и N-08 (11.09).
Статус: работает как межорганизационный форум с модерацией своей организации.
Стартует пустым: засеваются только разделы. Настоящая тема показывает реальное
имя автора, компанию, время и реакции; страница темы показывает полный текст,
не превью.

## Что сделано

- Модуль `apps/api/src/modules/community`, маршруты под `/community`: разделы,
  темы (список, карточка, создание, правка, удаление, реакция, закрепление),
  ответы (то же плюс «лучший ответ»), биржа (`exchange`, смена статуса заявки),
  мероприятия (список, карточка, запись), лидерборд.
- Типы тем: обсуждение, вопрос, объявление, заявка биржи, витрина. Заявка биржи
  несёт намерение (ищу/предлагаю/передаю клиента), сторону, локацию, сумму,
  комиссию, срок и статус.
- Темы, ответы и биржа видны всем организациям — так задуман модуль. Поэтому
  четыре его репозитория стоят в `NON_TENANT_REPOSITORIES` стража tenant-scope.
- Права — permission-matrix §1.8.

## Исправлено 10.09

- `c01688e`: при удалении темы и ответа в коде стояло `isModerator = true`.
  Грант `manage` есть почти у всех ролей, поэтому любая организация, в том числе
  только что зарегистрированная, удаляла чужие темы. Теперь модерация (удалить,
  закрепить, править чужое) действует только на контент своей организации.
  Закрепление проверяет организацию. «Лучший ответ» ищется только внутри своей
  темы. `threadId` и `pinned` из тела запроса проверяются на тип.
- `735bc4d` (ERP): при ошибке записи экран больше не показывает «опубликовано»;
  имена параметров совпадают с `ListCommunityThreadsQueryDto`; несуществующие
  `/community/tags/trending` и `/community/stats` не вызываются; текущий
  пользователь берётся из auth-контекста.

## Исправлено 11.09 (N-02): вымысел не выдаётся за данные

- **Засев.** При старте в пустые коллекции больше не пишутся выдуманные темы
  («Алексей Смирнов, Grand Realty», «Horizon Development») с накрученными
  просмотрами и мероприятия на октябрь «на 34 и 89 участников». Засеваются
  только шесть разделов: это структура площадки, через API раздел не создать.
- **Очистка баз, куда засев уже попал.** `seedDefaultsIfEmpty` при каждом старте
  удаляет записи с фиксированными id бывшего засева (`RETIRED_SEED_THREAD_IDS`,
  `RETIRED_SEED_EVENT_IDS` в `community-seed-data.ts`) и ответы под этими темами:
  без темы до ответа не добраться. Настоящие темы получают id
  `th-<timestamp>-<uuid>`, мероприятия через API не создаются, поэтому совпасть с
  фиксированными строками они не могут. Счётчики разделов не трогаются: засев
  их не увеличивал. Проверено на настоящей MongoDB
  (`test/integration/community-retired-seed.integration-spec.ts`): уходят ровно
  три темы, ответ под выдуманной темой и два мероприятия, живые темы и ответы
  остаются, повторный старт ничего не меняет.
- **Лидерборд.** `GET /community/leaderboard` отдаёт пустой список вместо трёх
  вымышленных людей с «индексом доверия 98». Описание добавлено в OpenAPI.
- **Закрепление при создании.** Поле `pinned` убрано из
  `CreateCommunityThreadDto`: `ValidationPipe` с `forbidNonWhitelisted` теперь
  отвечает 400, а сервис в любом случае создаёт тему незакреплённой.
  Закрепление — только `PATCH /community/threads/:id/pin` модератором своей
  организации. В OpenAPI этого поля в запросе и не было. ERP его не отправлял.
- **Автор.** Без снимка профиля автору больше не приписываются «Агентство
  недвижимости» и сегмент `broker`: остаётся «Участник BAZA».
- **ERP.** Список разделов в `forumData.ts` (`SECTIONS`) теперь зеркалит API. Раньше
  форма новой темы предлагала «Ипотеку», «Маркетинг», «Технологии» и
  «Нетворкинг». API этих разделов не знает, публикация в них падала с 404, а
  раздела «Кейсы и опыт» в форме не было. Расхождение ловит тест
  `apps/erp-web/tests/unit/communitySectionsSync.test.ts`. Иконки `briefcase` и
  `arrow-left-right` добавлены. Пустые панели «Ближайшие события» и «Топ
  недели» скрыты, раздел мероприятий пишет «Мероприятий пока нет».

## Исправлено 11.09 (N-08): автор из профиля, ERP читает ответ API

Найдено при разборе N-02 (документ уже описывал это как открытый пункт 1 и 2):
контроллер никогда не передавал снимок профиля (любая тема и ответ подписаны
«Участник BAZA» без компании), а `communityApi.ts` прокидывал сырой ответ API
как есть под видом мока, хотя имена полей не совпадали. У настоящей темы
(authorId — ObjectId, которого нет в демо-справочнике `MEMBERS`) это молча
давало пустую подпись автора, `undefined назад` вместо времени, нулевые
реакции и превью вместо полного текста.

- **Автор.** `CommunityService.buildAuthorSnapshot` читает
  `Position.currentOccupantName` (тот же денормализованный источник, что
  «Команда» в ERP, `team.service.ts::toView`) и `Organization.name`/`type`
  через новый `OrganizationsService.getPositionSummary` (тот же cross-module
  паттерн, что `getOrganizationById`). Сбой чтения не блокирует публикацию —
  откатывается на «Участник BAZA» без выдумки компании/сегмента. Имя позиции
  пустое до первого явного задания (тот же случай, что у только что созданного
  владельца, см. `team.service.ts`) — не подменяется дефолтом, компания при
  этом остаётся известной. Проверено на настоящей MongoDB
  (`test/integration/community-author-snapshot.integration-spec.ts`): реальные
  имя и организация уходят и в ответ API, и в сохранённый документ.
- **ERP: адаптер ответа API.** `communityApi.ts` маппит сырой ответ
  (`reactionCount`/`createdAt`/`author`) в форму, которую рисуют компоненты
  (`reactions`/`createdAgo`/`author`), во всех точках чтения и записи тем и
  ответов (`getThreads`, `getThreadById`, `createThread`, `updateThread`,
  `pinThread`, `getReplies`, `createReply`, `updateReply`,
  `getExchangeBoard`, `search`, `getMemberThreads`).
- **ERP: автор без ссылки в никуда.** `AuthorLine` показывает имя из
  реального снимка `author`, а не только из мок-справочника `MEMBERS`.
  Кликабельной подпись остаётся только для демо-участников (профиля по id
  настоящего автора нет — лидерборд пуст, см. открытый пункт ниже): для
  реального автора это статичный текст, не ссылка на «участник не найден».
- **ERP: полный текст темы.** Страница темы показывает `thread.body`
  (тот же текст, что принял `POST /community/threads`), не `thread.excerpt`
  (обрезанное превью для карточек списка) — оно и раньше отображалось на
  странице темы вместо полного поста.

## Почему модерация своей организации

`manage` — грант роли внутри организации, а не полномочие над чужим контентом на
общей площадке. Модерация всей площадки — задача админ-контура (этап 8, admin
grants). Пока её нет, чужой спам удалить некому.

## Что открыто

1. **Профиль участника по имени не открывается.** `GET /community/leaderboard`
   пуст (N-02) — страница участника ищет автора там и всегда пишет «не
   найден». Подпись автора у реальной темы/ответа теперь не кликабельна (см.
   N-08 выше) вместо ссылки в никуда, но это временная честная заглушка, не
   решение: связаться с автором заявки биржи по-прежнему нельзя, биржа по
   сути не работает. Нужен отдельный способ найти позицию/организацию
   автора (не лидерборд, который про рейтинг, а не про профиль).
2. **Текст темы не форматируется.** `thread.body`/`reply.body` — то же
   Markdown-сырьё, что принял `POST`, но рендерится как простой текст:
   `##`/`**` видны как есть. `react-markdown` уже в зависимостях проекта
   (используется в устаревшем `src/features/crm`, исключённом из сборки), но
   подключать его в форум — отдельное решение, не часть этого исправления.
3. **Тип «объявление» открыт всем.** `announcement` и `showcase` в форме помечены
   «компания», но сервер их не ограничивает.
4. ~~**Кто видит биржу.** Заявки видят все организации, включая
   застройщиков...~~ — закрыто 13.09.2026 (N-10). Биржу видят и создают
   только проверенные агентства и риэлторы (`Organization.mlsVerified`),
   застройщики — никогда, независимо от флага. Верификация — вручную
   администратором (`POST /admin/organizations/:id/verify-mls`), список
   проверяемых документов открыт для отдельного ADR. См.
   [mls-verification](mls-verification.md).
5. ~~Реакции и запись на мероприятия — «прочитал, изменил, сохранил»: при
   гонке обновления теряются.~~ — закрыто 11.09.2026.
   `CommunityThreadRepository`/`CommunityReplyRepository.toggleReaction`,
   `CommunityEventRepository.toggleAttendance` были read-modify-write без
   CAS: `find` → мутация в JS → `save()`. Два конкурентных toggle читали
   одно и то же состояние, и более поздний `save()` затирал документ
   целиком поверх более раннего — реакция терялась молча, не
   дублировалась. Проверено на настоящей MongoDB: 10 параллельных
   `Promise.all`-вызовов от разных участников на коде до фикса дали 1-2
   реакции из 10 (не 10) — воспроизвёл падение до фикса, затем применил
   его и убедился, что все 10 сохраняются. Теперь toggle — атомарный
   `findOneAndUpdate` с условным фильтром (сначала пробуем добавить с
   фильтром «меня там ещё нет», не совпало — пробуем убрать с фильтром «я
   там есть»); гонка на уровне MongoDB невозможна.
   [community-reaction-race.integration-spec.ts](../../apps/api/test/integration/community-reaction-race.integration-spec.ts).
6. `body` и `tags` без ограничений длины, поиск регэкспом по неиндексированному
   `body`, rate limit нет. Пагинация через offset вопреки ADR-007.
7. Мутации без аудита и без `expectedVersion`.
8. Поиск участников, статистика и популярные теги в ERP возвращают пустое:
   бэкенда для них нет.
9. Организации, созданные до 10.09, не имеют грантов community, пока в окружении
   не запущена доливка `grants:backfill-defaults` (N-06,
   [default-grants-backfill](default-grants-backfill.md)).
