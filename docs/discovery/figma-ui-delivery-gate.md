# BAZA.sale — Figma-only UI Delivery Gate

Статус: **обязательно для каждого marketplace UI-изменения с 26.08.2026**.

## Зачем это нужно

Marketplace переписывается по Figma. Цель этого документа — не допустить generic-интерфейсов, переносов визуального мусора со старого сайта и «логичных» дизайнерских догадок исполнителя.

Визуальная правда marketplace: Figma.  
Поведение, не отражённое в Figma: решение владельца и принятые продуктовые документы.  
Старый сайт: только инвентарь функций и SEO, не образец UI.

## Обязательная последовательность

### 1. До кода

Для конкретного route исполнитель создаёт запись в таблице ниже и заполняет все поля:

1. Figma URL и точный node ID конкретного фрейма.
2. Имя фрейма, его desktop/mobile-варианты и интерактивные состояния.
3. Список компонентных вариантов, которые реально используются на экране.
4. Привязку к файлам реализации.
5. Явные Figma gaps: отсутствующие loading/empty/error/forbidden/conflict-состояния, спорные варианты, `(не используется)`.

Без этой записи UI-код не начинается.

### 2. Во время реализации

- Снимать размеры, сетку, отступы, typography, цвета, радиусы, границы и hover/focus/disabled из Figma или Figma component/variable styles.
- Реализовывать только подтверждённые блоки и взаимодействия.
- Не переносить HTML/CSS/визуальный паттерн со старого `baza.sale`.
- Не создавать "улучшающий" hero, выдуманные карточки, декоративные иллюстрации, fake stock imagery, фейковые метрики или несуществующие фильтры.
- Не применять Hallmark, шаблонные UI-подходы или произвольную новую палитру как замену Figma. Они допустимы только для технической реализации уже подтверждённого Figma-решения и не могут менять композицию.
- Если данных API не хватает для Figma-блока, зафиксировать backend gap; не скрывать его placeholder-данными и не менять дизайн под ограничение API без решения владельца.

### 3. Перед сдачей

1. Снять screenshot реализации в размерах соответствующего Figma-фрейма.
2. Сверить визуально с Figma: layout, header/footer, сетка, размеры карточки, цвета, шрифты, states, mobile.
3. Записать результат сверки и известные backend/Figma gaps в таблицу.
4. Проверить минимум desktop и Figma mobile-вариант. Если mobile в Figma отсутствует — явно отметить это.
5. Только после этого статус может стать `ready for owner review`.

> **Поправка владельца от 04.09.2026: шаги 2–5 переносятся в конец.**
>
> «Сверять и править будем, когда всё закончим». Визуальная сверка с фреймами и
> правки по её итогам делаются одним проходом по всем экранам после того, как
> вёрстка закончена, а не по каждому пакету изменений.
>
> **Что при этом продолжает действовать без исключений:** пункты раздела «1. До
> кода» (точный node ID до начала работы), все запреты раздела «2. Во время
> реализации» и шаг 1 выше — скриншот снимается сразу, скриптом
> `apps/e2e-runtime/scripts/capture-marketplace-screens.mjs`. Отложена именно
> сверка, а не дисциплина по макетам: без node ID и с выдуманной вёрсткой сверять
> в конце будет нечего.
>
> **Чем это оплачивается, чтобы решение было принято с открытыми глазами.**
> Дефект, найденный на одном экране, к моменту сверки уже разойдётся по всем
> остальным. Это не гипотеза: иконки категорий сделаны эмодзи вместо библиотеки
> из UI kit `40:4517`, и каждый новый экран, свёрстанный до сверки, унаследует
> тот же приём. Правка в конце будет стоить дороже, чем те же правки по ходу.
> Решение владельца это признаёт и принимает.

## Definition of Done для marketplace UI

- [ ] Есть точный Figma node ID и ссылка.
- [ ] Подтверждены используемые desktop/mobile-фреймы.
- [ ] Нет выдуманной визуальной структуры или дизайна.
- [ ] Все подтверждённые Figma states реализованы.
- [ ] Отсутствующие в Figma states отмечены как gap и согласованы/следуют принятому DoD.
- [ ] Скриншот снят в габаритах фрейма (сразу, по каждому пакету).
- [ ] Screenshot implementation сопоставлен с Figma — **отложено в финальный
      проход по решению владельца от 04.09.2026**, см. поправку в разделе
      «3. Перед сдачей». Пункт остаётся обязательным для перевода экрана в
      `ready for owner review`, просто выполняется один раз по всем экранам.
- [ ] Функциональные API-gaps вынесены отдельным списком, а не замаскированы.
- [ ] Typecheck/test/build пройдены.

>   с реестром узлов: имена и габариты сходятся.
> - **Этап 2 (решения владельца)**: **завершён 04.09.2026, все семь пунктов
>   закрыты.** Документ `figma-owner-decisions-stage2.md` сначала был помечен
>   «УТВЕРЖДЕНО» с основанием «делегирование выбора владельцем на основе
>   экспертной оценки», то есть выбор сделал исполнитель, а гейт это запрещает
>   прямо. Документ переоформлен в запрос, после чего владелец ответил по всем
>   пунктам: главную отделить от каталога по образцу действующего `baza.sale`;
>   макет детальной страницы ЖК живой, верстать по нему; подвал единый; рейтинг
>   риэлторов в полной версии; отдельных страниц компаний не делать, клик ведёт в
>   отфильтрованный каталог; недостающие состояния достраивать по стилистике UI
>   kit; встроенный CRM риэлтора не делать.
> - **Этап 3 (UI-код)**: код 20 экранов написан, `tsc -b` чистый, 33 тест-файла и
>   153 теста зелёные. **Но ни один экран по гейту не сдан.** Скриншоты сняты
>   (`screenshots/`, 24 файла), а сопоставление с фреймами Figma человеком не
>   выполнялось: по решению владельца от 04.09.2026 сверка идёт одним проходом в
>   конце. Статус каждой строки ниже — `scaffold`, как требует гейт до сверки.
>
> **Три экрана собраны из токенов UI kit, а не по фрейму** — `MKT-SCR-013` (вход
> и регистрация), `MKT-SCR-027` (страница «не найдено») и системные состояния
> внутри каталога. В Figma этих фреймов нет, это зафиксированные gap'ы, сборка
> разрешена владельцем. Сверять их в финальном проходе не с чем: проверять надо
> согласованность с остальными экранами, а не совпадение с макетом.
>
> **Что важно не перепутать при приёмке.** Прежний статус «Verified in code» гейт
> не определяет. Он означал «код написан», а не «перенос дизайна проверен». Эти две
> вещи на приёмке подменять друг друга не должны.
>
> **Встроенный CRM риэлтора отменён владельцем 04.09.2026** («вообще бред, такого
> не будет»). Экраны воронки, задач и календаря (`MKT-SCR-022`, `023`, `024`)
> удалены вместе с маршрутами, тестами и скриншотами. Вопрос был поставлен потому,
> что наличие фреймов в Figma говорит лишь о том, что дизайнер их рисовал, а не о
> том, что компания ведёт второй CRM при живом ERP.
>
> **`MKT-SCR-019` остаётся сделанным авансом.** По фазовке
> `marketplace-screen-build-spec.md` §7 кабинет «Мои объекты» относится к фазе P2, а
> P0 по гейту ещё не сдан.
>
> **Шестнадцать экранов на реальном API, два на фикстурах.** Каталоги,
> детальные страницы, раскрытие контакта, кабинет «Мои объекты», редактирование
> объявления и клиентская страница подборки ходят в backend. На захардкоженных
> массивах остались запросы и профиль риэлтора (`INITIAL_REQUESTS`,
> `MOCK_REVIEWS`); список подборок агента
> (`INITIAL_COLLECTIONS`) тоже, но это ERP-территория.
>
> Клиентская страница подборки переписана 04.09.2026. До этого она была
> захардкоженной вёрсткой, игнорировала токен из ссылки и всем показывала одно и
> то же: выдуманные объекты, выдуманного эксперта «Георгий Беридзе» и выдуманный
> номер WhatsApp. Человек, которому агент прислал ссылку, видел не свою подборку,
> а декорацию с чужими контактами. Публичный эндпоинт при этом существовал —
> не хватало данных объектов в его ответе, они добавлены.
>
> Кабинет снят с фикстур 04.09.2026 вместе с редактированием объявления. Вместе с
> выдуманными объектами оттуда ушли счётчики просмотров, контактов и добавлений в
> избранное: таких полей нет в API, и показывать вместо них правдоподобные числа
> значило врать владельцу о его собственных объектах. Разметка блока сохранена и
> включится сама, когда поля появятся — это API gap, записанный отдельно, как и
> требует гейт.

## Скриншоты и visual compare

Снимки делает шаг `Capture marketplace screenshots` сквозного гейта
(`.github/workflows/runtime-release-gate.yml`) — на поднятом стеке, с реальными
данными, артефактом `marketplace-screenshots`. Текущий комплект от 05.09.2026
лежит в `docs/discovery/screenshots/`: 17 экранов в двух брейкпоинтах, 34 файла,
машинный отчёт `capture-report.json`.

Чек-лист сверки, по строке на экран с ID фреймов и открытыми вопросами, —
[figma-visual-compare-checklist.md](figma-visual-compare-checklist.md).

Скриншоты снимаются по ходу, а сверка с фреймами выполняется одним проходом в
конце — поправка владельца от 04.09.2026, см. раздел «3. Перед сдачей».

Это закрывает половину пункта DoD: материал для сверки есть. Вторая половина,
сопоставление с фреймами, остаётся за человеком с открытой Figma, поэтому
статусы в таблице выше остались `scaffold`.

### Чего в комплекте нет

- Разделы кабинета (`MKT-SCR-019`, `020`, `021`) теперь снимаются под сессией и
  с собственным объектом аккаунта. До этого пять прогонов подряд они выходили
  формой входа, и причина оказалась не в съёмке: войти в кабинет было нельзя
  вообще.
- **Пять экранов реестра** снимаются не как страница: header, footer, фасетные
  фильтры и CTA раскрытия контакта видны внутри других снимков, а модалка
  быстрого просмотра юнита не снимается вовсе — она открывается кликом по юниту,
  а юнитов у засеянного ЖК нет.

### Что нашлось благодаря снимкам

Каждый пункт всплыл только потому, что экран впервые сняли.

- **Выдуманные данные объектов убраны.** На детальной странице любого ЖК
  показывались четыре квартиры с площадями и ценами и блок «Стоимость квартир:
  от $39 000, от $1 200 / м², возможна беспроцентная рассрочка»; на карточке ЖК —
  плашка «от 32 м²». Всё это было вписано в код и одинаково у всех комплексов.
  Юниты не публикуются (воркер помечает такие события `build_failed`), поэтому
  страница теперь говорит, что планировки появятся после публикации.
- **Бейдж «Продажа» на детальной был зелёным по зелёному**: элемент несёт и
  `.listing-badge` из `app.css`, и `.figma-listing-card__badge--deal`,
  специфичность равная, побеждал порядок подключения. В каталоге дефекта не было.
- **Токен `--color-main` не существовал**: двадцать одно объявление держалось на
  fallback `#1BA800`, то есть брендовый зелёный был вписан хексом в двадцати
  одном месте.
- **Иконки категорий сделаны эмодзи**, хотя в UI kit `40:4517` есть иконочная
  библиотека. Не исправлено: нужны сами иконки из макета.
- **Исправлено раньше, 04.09.2026:** активная вкладка поиска на главной была
  зелёной по зелёному (`.home-hero__tab.is-active` перебивал
  `.figma-home-search-tab.is-active` по порядку подключения) и семь токенов,
  которых не стало при переезде `tokens.css` на значения из Figma
  (`--color-accent-ink`, `--color-surface`, `--color-building-window`,
  `--space-12/16/20`, `--text-2xl`) — объявления с ними были невалидны, отсюда
  нечитаемая кнопка «Повторить попытку». Токены возвращены и помечены как
  невыверенные.

## Решения владельца (Этап 2, закрыт)

Все семь пунктов закрыты 04.09.2026, ответы и обоснование выбора —
**[figma-owner-decisions-stage2.md](figma-owner-decisions-stage2.md)**.
Спорных решений по макетам не осталось, угадывать больше нечего.

**Что это меняет для приёмки, а что нет.** Разблокирован Этап 3 по существу:
исполнитель знает, по каким фреймам верстать. Но статус экранов остаётся
`scaffold` — он снимается не решением владельца, а visual compare, которого пока
не было.

**Один пункт стоит помнить.** Узел `3314:200742` в Figma по-прежнему называется
`ЖК целая страница (не используется)`. Владелец подтвердил, что пометка
неактуальна и макет живой. Имя узла при этом не изменилось, поэтому следующий,
кто откроет файл, увидит ту же пометку — ответ записан в документе решений, чтобы
не спрашивать второй раз.

### Расхождения, найденные при сверке с реестром узлов (04.09.2026)

Node ID из таблицы выше сверены с `figma-node-registry.json`. Большинство сходится
точно: `3428:55239` это `Home page` 1920x5544, `3067:73634` это `footer 1` 1920x640,
`236:27197` это `search result (2 page) full width` 1920x1216. **Все три
расхождения закрыты в тот же день**, ни одно не осталось открытым.

| Экран | Что было не так | Чем закрыто |
| --- | --- | --- |
| `MKT-SCR-007` | Имя узла `3314:200742` буквально `ЖК целая страница (не используется)`: в работу взят основной экран каталога, помеченный дизайнером как неиспользуемый. Прежнее объяснение («пометка возникла при исследовании соседней карточки `4182:62649`») было предположением о намерении дизайнера, а не фактом из файла. | Решением владельца: макет живой, пометка неактуальна, верстать по нему. Имя узла в Figma при этом не изменилось. |
| `MKT-SCR-022` | `3760:57807` называется `клиенты`, а не воронка канбан. | Экран удалён: владелец отменил встроенный CRM. |
| `MKT-SCR-023` | `3927:57386` имеет габариты 742x333, то есть полноэкранная страница задач была собрана из блока размером с виджет. | Экран удалён вместе с остальным встроенным CRM. |

Общий вывод из сверки: колонку «Figma URL + node ID» стоит перепроверить целиком.
У удалённых CRM-строк там стояли не секции, а произвольные фреймы, и один и тот же
ID был указан сразу и как секция, и как десктопный фрейм. Ошибка того же рода
может сидеть и в оставшихся строках.

## Формат отчёта исполнителя

Вместо фразы «сделал страницу» вернуть только:

1. Figma refs: URL + node IDs.
2. Реализованные файлы.
3. Что совпало с Figma.
4. Какие states/детали отсутствуют в Figma и как они были согласованы.
5. Screenshot paths и результат visual compare.
6. Backend gaps, которые мешают точному переносу.
